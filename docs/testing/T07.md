## Environment
Node 24.22.3, Chromium (Playwright), real relay server built from this branch (`createTincanServer` from `server/dist`, real CSP and headers). There is no UI yet, so there are no screenshots.

Throwaway harness (kept outside the repo): `relay.service.ts` and its socket factory bundled with esbuild into a page that is served by the relay itself as `clientDir`, so it is same-origin and runs under the real CSP (`script-src 'self'`, `connect-src 'self'`, Trusted Types). Angular DI is bypassed with a small `Injector` and `runInInjectionContext`. The page polls `status`, `peer`, `ended` and `protocolErrorCount` every 10 ms and subscribes to all four observables. Two Playwright pages (sender, receiver) in separate contexts, each reaching the server through its own TCP proxy that can reset every connection and refuse new ones. That drops a link the way a real network does, per side, and keeps the browser's own reconnect logic in play. Tokens were read from the WebSocket frames over CDP so the leak check knows what to look for. Frames are `{ v: 1, seq, iv, ct }` with random canonical base64url of legal length (the relay treats them as opaque). 37 checks, all passed.

## Not covered / follow-ups
- No UI, so no screenshots, keyboard or viewport checks (T08 to T10).
- Network loss was simulated with TCP resets at a proxy, not with Chromium's offline emulation, which does not close an established WebSocket; the effect on the service is the same transport close.
- Tab close or reload (`pagehide` calling `leave()`) is a T10 concern, noted in the task Log.
- Ack timeout (8 s) and connect timeout (10 s) were not run against a stalled real server; they are covered by the fake-socket unit tests.
- `keepLatest` frames are numbered by the caller; the service does not renumber, so a caller that reuses a lower seq after resume would be rejected by the relay (`bad_request`).
